Garden Automation Robot — Project Plan

A living plan for a garden robot built as a reusable navigation + compute foundation, not a single-task machine — so each new capability (weed cutting, then whatever comes after) reuses the driving, mapping, and command-parsing work already done instead of starting over. Grounded in the actual parcel — Xoirostasio (Kipos), 6,255m² (6.26 stremmata) — from the Home Savings Guide: annual beds, a young orchard, rotationally-grazed chickens, and a compost/cover-crop strip, terraced across a slope on a plot separate from home. It already carries 13 owner-confirmed olive trees at deliberately low density and has a farm building on or adjacent to it. The vineyard and main olive grove elsewhere on the property stay out of scope here for now.

How to read this page: the first sections lay out the architecture, hardware, and build order as a reference. The last section, "Design Studio," is where the actual robot-by-robot decisions get made — most of it starts as open questions on purpose, to be filled in over future sessions rather than guessed at now.

Your Garden, As the Robot Would See It

No bed-by-bed map yet — which terrace gets which use (beds, orchard, chicken rotation) hasn't been planned. But the parcel records fix real, specific facts about the ground itself that change the robot's design more than any layout would: the property's terraces come in three distinct types, not one uniform "sloped ground" — stone-walled terraces, cut/dug dirt terraces (a vertical soil face, more erosion-prone right at the cut), and raw un-terraced slope at roughly 60% grade (~31°) with trees planted directly on it. Access today is on foot only once past the edge of a parcel — a vehicle reaches the lower part, nothing more — and the steepest sections are, in the owner's own words, hard to stay in control of even walking. That's a real safety boundary for a machine with a cutting head, not a detail to gloss over. The diagram below reflects this typology directly rather than a generic staircase.

Schematic, not a real map — but the terrace types, the raw-slope grade, and the farm building are real facts from the parcel records, not placeholders.

Three things this changes from a flat-ground assumption. First, mobility has to deal with stepped terraces of genuinely different character — stone-walled terraces are the most stable footing, dirt-cut terraces need care near the exposed soil face, and the raw ~60% slope is realistically off-limits to a wheeled or tracked ground robot entirely; the property's own notes already flag mule/manual work or a monorail-type transporter for the steepest ground, which is the honest answer there rather than forcing a general-purpose chassis to handle it. Second, the chicken problem is a scheduling problem, not a detection problem: since a section is either "chickens active this rotation" or "robot working," the robot just needs to know which terraces are chicken-active right now and stay out — no live chicken detection needed. Third, there's now a real candidate site for the brain server and charging dock: the existing farm building on/adjacent to the parcel, rather than an assumed shed that may or may not exist.

The Brain: Server Hardware

The plan's own split — a cheap always-on mini-PC for 24/7 inference, an existing GPU machine spun up only occasionally for training — is the right shape for this garden's scale (one robot, a handful of small models, low-frequency commands). The numbers below are a rough starting estimate, not a spec sheet to buy against blindly; treat them the way the Home Savings Guide treats its cost ranges.

Always-on brain (new purchase)

€250-400 total N100/N305-class mini-PC, 16GB RAM, 512GB NVMe

An Intel N100 or N305 mini-PC (Beelink/GMKtec-type boxes, roughly €150-220 barebones with 16GB) has no real GPU, but that's fine for this job: a small quantized command-parsing LLM (1-3B parameters, via llama.cpp or similar) runs adequately on CPU at low query volume — you're issuing occasional commands, not holding a live conversation — and small detection models (YOLO-nano/small) run at a few frames per second, which is plenty for a robot that revisits waypoints every couple of days rather than needing real-time high-fps vision. Go to 32GB RAM (~€30-50 more) if running the LLM, a vision model, navigation service, and dashboard concurrently starts to feel tight — cheap insurance against swapping to disk. A 512GB-1TB NVMe SSD (~€40-70) covers model weights, the waypoint database, failure logs, and a rolling window of training images/clips before they get pulled off for the occasional training run.

Optional: vision accelerator

€60-120 optional, add later if CPU inference feels slow

A USB accelerator (Coral Edge TPU or a Hailo-8 module) offloads detection-model inference from the N100's CPU, useful once there's more than one vision task running or the "scan at transit speed" optimization from the plan's weeding section is worth doing. Not needed to get started — worth adding once step 6 (first vision task) is actually built and its real speed is known, not before.

Connectivity — deliberately open for now

deferred — settle once terraces and site logistics are known

The plot is separate land, not next to home, so this isn't a "does home WiFi reach the garden" problem — it's a standalone-site connectivity problem. Still not sizing this now on purpose, but there's a real anchor point worth checking first: the existing farm building on/adjacent to the parcel. If it already has power or a phone line, that's the natural place to base a WiFi AP or point-to-point bridge from; if it's genuinely off-grid, that pushes toward a cellular modem or a LoRa link for a low-bandwidth command/telemetry channel instead. Revisit this once it's known whether that building has power, and where the robot's home base actually sits relative to it.

Charging dock power

€50-300 check the existing farm building for power before assuming solar

Since the plot isn't adjacent to home, a fresh mains cable out to a charging dock is unlikely to be the easy option — but the parcel already has a farm building on/adjacent to it, so the real first step is checking whether that building has power before assuming anything. If it does, this is just a weatherproof outlet and enclosure (~€50-100). If it doesn't, a small solar panel + battery trickle-charge setup (~€150-300) is the fallback for a low-power charging load like this. Worth confirming which case applies once the dock's location is picked — likely near that building either way.

Existing GPU machine (training, occasional use)

already have 8GB+ VRAM is enough for this scale

Training small per-task detection models (YOLOv8n-scale) doesn't need a lot of VRAM — 8GB is comfortable, even 6GB works with a small batch size. Its job here is narrow: pull labeled images off the brain server occasionally, train or fine-tune one small model, push the result back into the model registry. No need to upgrade this machine before starting; revisit only if a specific future model turns out to need more.

Software Architecture

This is the plan's own two-layer split, drawn out with the pieces that actually run on each machine and how a command flows through the system end to end.

Solid arrows = live data paths. Dashed arrows = occasional/offline paths (training, log review).

Following one command through the system: you type or say "cut the weeds by the tomatoes" into the dashboard. The LLM command parser turns that into a function call — goto("tomato_bed") then run_task("weed_cut") — by matching against the waypoint database's gazetteer entries, nothing more. The navigation service (plain deterministic code, no AI) computes the route and streams motion commands to the robot; the robot drives and streams back telemetry and video. Whatever vision the task needs (checking stem thickness near a recorded plant coordinate, say) goes through one small model from the registry, not the LLM — the LLM never sees pixels. Anything the system can't resolve — an unrecognized location name, an ambiguous instruction — gets written to the failure log instead of guessed at, and that log is what actually drives development: reviewed offline, periodically, to decide what to hardcode next or what small model to train. Home Assistant sits at the same level as the navigation service and vision registry — just more functions the parser can call — so "turn on the drip line to the almond row" is handled the same way as a robot command, no separate system.

Design Studio

This is where the actual per-robot decisions happen, over however many future sessions it takes. Each card below has a status, what's already settled, and — the important part — the open questions still needing an actual decision. Nothing here is final; it's the working state of the design as of today.

Robot 1 — The Weeder

Designing now

The plan's own concrete first task: cut weeds among deliberately-oversized transplants in the annual beds, by revisiting known coordinates and keeping the thicker of any two nearby stems — no weed-vs-crop classification needed. This is the one to actually spec first, since it's what steps 1-6 above are all in service of.

Garden-specific constraints

  • Three real terrace types on this land — stone-walled, dirt-cut, and raw ~60% slope — and which terrace holds which bed isn't planned yet, so exact chassis sizing waits on that; but the raw-slope type is realistically off-limits to any wheeled/tracked robot regardless of layout.
  • Access today is on foot past the edge of a parcel — no vehicle track through it — and the steepest ground is hard to stay in control of even walking, per the owner's own notes. That's a hard exclusion zone for the robot, not just a rough patch to slow down for.
  • Chickens are rotated through one fenced terrace/section at a time, never the whole plot — as long as the robot's schedule and the chicken rotation schedule are kept mutually exclusive per section, no live chicken detection or avoidance is needed at all.
  • Bed spacing and soil surface (raised beds vs. flat) aren't nailed down on this page yet — affects wheel/track choice and ground clearance.
  • Revisits every ~2 days per the plan — cadence affects battery/charging-dock sizing.

Open questions to settle together

  • Does one robot cross terraces via ramps, stay within one terrace and get repositioned by hand/trailer, or is a monorail-type transporter (already the property's own fallback idea for the steepest ground) worth considering for terrace-to-terrace movement generally?
  • Chassis: wheels vs. tracks, given stone-walled vs. dirt-cut terrace surfaces — can these two types share one chassis design, or does the dirt-cut terrace's erosion-prone edge need different handling?
  • Cutting mechanism: trimmer-head, small blade, or something else?
  • How is a plant's coordinate actually recorded at transplant time — a phone app, the robot itself in a "mark" mode, something else?
  • How does the system know which terrace/section is chicken-active right now — a manual toggle, a schedule, something tied to the fencing?
  • Does the existing farm building become the robot's charging dock, or is a separate dock better positioned relative to the beds once they're planned?

Robot 2 — The Scout

Idea, not started

The plan's own optional optimization: a lightweight, camera-only robot (no cutter, less power, cheaper) that pre-maps where attention is actually needed each pass, feeding a task list to the Weeder instead of it cutting every bed uniformly every time.

Open questions to settle together

  • Worth building at all before the Weeder's real cadence and coverage time are known from experience?
  • Shared chassis platform with the Weeder, or deliberately different (smaller, faster, no payload mount)?
Next step: revisit once the Weeder has real-world runtime data — this may turn out unnecessary.

Precision Orchard Work

Future — needs the foundation first

The plan flags precision vine pruning as hard: recognition is easy, precise manipulation on a springy target is the real problem. Mapped to this garden, the nearest equivalent is bud-level work on the 13 confirmed olive trees already on this parcel (deliberately low density, no more planned) plus whatever lemon/orange/pomegranate/almond trees join them as the wider garden plan fills in — olive pruning specifically is already an active, hands-on skill elsewhere on the property's main grove, so there's real technique to eventually encode here, not a blank slate.

Open questions to settle together

  • Realistically years out given this is robot #3+ in the build order — worth a placeholder now or revisiting later?
  • Worth pulling in the pruning conventions already used on the main grove once this gets designed, rather than inventing a fresh approach?
Next step: nothing to decide yet — parked until the Weeder and Scout are real.

Closed-Loop Precision Watering

Future

Per the plan, this needs a flow sensor or load cell for accurate volume — not vision. Could ride on the Weeder's chassis as a second payload (step 7's "repeat" in action) once it exists, watering exactly at a recorded plant coordinate rather than a whole zone.

Open questions to settle together

Smart Irrigation Valves

No robot needed — can start anytime

One of the plan's own "easy wins": multi-zone valves with different schedules per bed/orchard row, solved by existing off-the-shelf tech. Genuinely worth doing before or alongside any robot work, since it needs none of the navigation/LLM foundation above — and the parcel records already answer part of the design: water comes from the metered local utility, gravity feed is workable given the slope (no pump needed), but pressure-compensating (PC) emitters are close to mandatory, since the elevation change across a terrace run would otherwise starve the top of each run while flooding the bottom.

Open questions to settle together

  • How many zones does the real layout need — one per bed cluster, one per orchard row group, plus one for the compost strip's cover crop?
  • Tie into Home Assistant now, so it's already a callable function once the robot architecture exists?
  • Does the owner's separately-noted plan for a rain-fed cistern/pond factor into this parcel's zones, or is that sized for the wider property?
Next step: worth speccing this one independently of the robot timeline — it pays off immediately either way, and PC emitters are now a settled requirement, not an open question.

Fixed Sensors + Dashboard

No robot needed — can start anytime

The plan's other easy win: soil moisture sensors and a static camera on one area, feeding a garden-monitoring dashboard to cut down on manual checking walks. This dashboard is also exactly what step 4+ of the robot build order needs anyway — worth building once and reusing.

Open questions to settle together

  • Which spots get a fixed sensor first — the annual beds (higher water need, more attention) or the orchard (lower frequency, but a bigger area to check)?
  • Same dashboard as the robot's status/API from the architecture above, or a separate simpler one to start?
Next step: good candidate to build in parallel with the Weeder — shares no hardware, so it doesn't block or get blocked by robot decisions.
