Garden Automation Robot — Project Plan

A living plan for a garden robot built as a reusable navigation + compute foundation, not a single-task machine — so each new capability (weed cutting, then whatever comes after) reuses the driving, mapping, and command-parsing work already done instead of starting over. Grounded in the actual 6,000m² village garden from the Home Savings Guide: annual beds, a young orchard, free-ranging chickens, and a compost/cover-crop strip — separate from the vineyard and olive grove elsewhere on the property, which stay out of scope here for now.

How to read this page: the first sections lay out the architecture, hardware, and build order as a reference. The last section, "Design Studio," is where the actual robot-by-robot decisions get made — most of it starts as open questions on purpose, to be filled in over future sessions rather than guessed at now.

Your Garden, As the Robot Would See It

Everything the robot does — navigation, the waypoint gazetteer, the first weeding task — is anchored to the real layout of the 6,000m² plot, not a generic garden. Roughly, from what the Home Savings Guide already established: a cluster of annual beds (tomatoes, sweet corn, pumpkin/squash, dry legumes, herbs and alliums) that get replanted each season and are the most labor-hungry part of the garden; a young orchard (lemon, orange, olive, pomegranate, almond, fig) planted in rows with wide spacing, still years from full canopy; chickens free-ranging through both rather than penned in one spot; and a cover-crop/compost strip along an edge. The vineyard and existing olive grove live elsewhere on the property and aren't part of this robot's territory.

Schematic, not to scale. The dashed oval is deliberately loose — chickens roam, so the robot treats the whole worked area as "may contain a chicken" rather than mapping them as a fixed zone.

The two things this map makes concrete: the gazetteer (named waypoints from step 3 of the build order) starts as bed corners and tree rows, not abstract coordinates — "the tomato bed," "orchard row 2," "the compost strip" are entries a person can actually say out loud. And free-ranging chickens are a real, moving obstacle the robot has to tolerate everywhere in the worked area, not something solved once and forgotten — worth treating as a basic safety requirement (slow-moving, obstacle-stopping) from day one rather than an edge case.

The Brain: Server Hardware

The plan's own split — a cheap always-on mini-PC for 24/7 inference, an existing GPU machine spun up only occasionally for training — is the right shape for this garden's scale (one robot, a handful of small models, low-frequency commands). The numbers below are a rough starting estimate, not a spec sheet to buy against blindly; treat them the way the Home Savings Guide treats its cost ranges.

Always-on brain (new purchase)

€250-400 total N100/N305-class mini-PC, 16GB RAM, 512GB NVMe

An Intel N100 or N305 mini-PC (Beelink/GMKtec-type boxes, roughly €150-220 barebones with 16GB) has no real GPU, but that's fine for this job: a small quantized command-parsing LLM (1-3B parameters, via llama.cpp or similar) runs adequately on CPU at low query volume — you're issuing occasional commands, not holding a live conversation — and small detection models (YOLO-nano/small) run at a few frames per second, which is plenty for a robot that revisits waypoints every couple of days rather than needing real-time high-fps vision. Go to 32GB RAM (~€30-50 more) if running the LLM, a vision model, navigation service, and dashboard concurrently starts to feel tight — cheap insurance against swapping to disk. A 512GB-1TB NVMe SSD (~€40-70) covers model weights, the waypoint database, failure logs, and a rolling window of training images/clips before they get pulled off for the occasional training run.

Optional: vision accelerator

€60-120 optional, add later if CPU inference feels slow

A USB accelerator (Coral Edge TPU or a Hailo-8 module) offloads detection-model inference from the N100's CPU, useful once there's more than one vision task running or the "scan at transit speed" optimization from the plan's weeding section is worth doing. Not needed to get started — worth adding once step 6 (first vision task) is actually built and its real speed is known, not before.

Connectivity — the part the plan doesn't size, and 6,000m² makes real

€150-300 outdoor mesh/point-to-point + a cheap long-range fallback

A single home WiFi router will not reliably cover 6,000m² of outdoor, tree-obstructed ground — this is worth solving deliberately rather than discovering it as a dead zone once the robot is built. Two outdoor-rated access points (~€60-100 each, one at the house, one near the charging dock as sketched on the map above) with overlapping coverage handles video/telemetry over most of the property; a directional point-to-point bridge (Ubiquiti airMax-type gear, ~€50-90 a side) is the alternative if the layout is better served by one strong link than two overlapping circles. Worth adding a cheap LoRa pair (~€10-20) as an independent low-bandwidth fallback channel for basic telemetry and an emergency-stop command — it won't carry video, but it keeps working in a WiFi dead spot or AP outage, which matters more for a machine with blades or moving parts than it would for a pure sensor gadget.

Charging dock power

€100-300 depends on whether mains already reaches a garden shed

If a shed or outbuilding near the dock already has mains power, this is just a weatherproof outlet and enclosure (~€50-100). If not, a small solar panel + battery trickle-charge setup (~€150-300) avoids running a mains cable across the property — genuinely worth it for a low-power charging load like this, less obviously worth it if the robot ever needs to fast-charge.

Existing GPU machine (training, occasional use)

already have 8GB+ VRAM is enough for this scale

Training small per-task detection models (YOLOv8n-scale) doesn't need a lot of VRAM — 8GB is comfortable, even 6GB works with a small batch size. Its job here is narrow: pull labeled images off the brain server occasionally, train or fine-tune one small model, push the result back into the model registry. No need to upgrade this machine before starting; revisit only if a specific future model turns out to need more.

Software Architecture

This is the plan's own two-layer split, drawn out with the pieces that actually run on each machine and how a command flows through the system end to end.

Solid arrows = live data paths. Dashed arrows = occasional/offline paths (training, log review).

Following one command through the system: you type or say "cut the weeds by the tomatoes" into the dashboard. The LLM command parser turns that into a function call — goto("tomato_bed") then run_task("weed_cut") — by matching against the waypoint database's gazetteer entries, nothing more. The navigation service (plain deterministic code, no AI) computes the route and streams motion commands to the robot; the robot drives and streams back telemetry and video. Whatever vision the task needs (checking stem thickness near a recorded plant coordinate, say) goes through one small model from the registry, not the LLM — the LLM never sees pixels. Anything the system can't resolve — an unrecognized location name, an ambiguous instruction — gets written to the failure log instead of guessed at, and that log is what actually drives development: reviewed offline, periodically, to decide what to hardcode next or what small model to train. Home Assistant sits at the same level as the navigation service and vision registry — just more functions the parser can call — so "turn on the drip line to the almond row" is handled the same way as a robot command, no separate system.

Design Studio

This is where the actual per-robot decisions happen, over however many future sessions it takes. Each card below has a status, what's already settled, and — the important part — the open questions still needing an actual decision. Nothing here is final; it's the working state of the design as of today.

Robot 1 — The Weeder

Designing now

The plan's own concrete first task: cut weeds among deliberately-oversized transplants in the annual beds, by revisiting known coordinates and keeping the thicker of any two nearby stems — no weed-vs-crop classification needed. This is the one to actually spec first, since it's what steps 1-6 above are all in service of.

Garden-specific constraints

  • Needs to operate around free-ranging chickens anywhere in the worked area — a hard stop-on-obstacle requirement, not optional.
  • Bed spacing and soil surface (raised beds vs. flat) aren't nailed down on this page yet — affects wheel/track choice and ground clearance.
  • Revisits every ~2 days per the plan — cadence affects battery/charging-dock sizing.

Open questions to settle together

  • Chassis: wheels vs. tracks, given actual bed terrain and path width between beds?
  • Cutting mechanism: trimmer-head, small blade, or something else — and how it fails safely around a chicken or a foot?
  • How is a plant's coordinate actually recorded at transplant time — a phone app, the robot itself in a "mark" mode, something else?
  • Which beds get this first — all of them at once, or one crop (tomatoes, say) as the pilot?

Robot 2 — The Scout

Idea, not started

The plan's own optional optimization: a lightweight, camera-only robot (no cutter, less power, cheaper) that pre-maps where attention is actually needed each pass, feeding a task list to the Weeder instead of it cutting every bed uniformly every time.

Open questions to settle together

  • Worth building at all before the Weeder's real cadence and coverage time are known from experience?
  • Shared chassis platform with the Weeder, or deliberately different (smaller, faster, no payload mount)?
Next step: revisit once the Weeder has real-world runtime data — this may turn out unnecessary.

Precision Orchard Work

Future — needs the foundation first

The plan flags precision vine pruning as hard: recognition is easy, precise manipulation on a springy target is the real problem. Mapped to this garden, the nearest equivalent is bud-level work on the young lemon/orange/olive/pomegranate/almond rows once they're established enough to need it.

Open questions to settle together

  • Realistically years out given the orchard's current age — worth a placeholder now or revisiting later?
Next step: nothing to decide yet — parked until the Weeder and Scout are real.

Closed-Loop Precision Watering

Future

Per the plan, this needs a flow sensor or load cell for accurate volume — not vision. Could ride on the Weeder's chassis as a second payload (step 7's "repeat" in action) once it exists, watering exactly at a recorded plant coordinate rather than a whole zone.

Open questions to settle together

  • Does this replace or complement the smart irrigation valves below?
Next step: hold until the Weeder's payload mount design is settled, since this would likely reuse it.

Smart Irrigation Valves

No robot needed — can start anytime

One of the plan's own "easy wins": multi-zone valves with different schedules per bed/orchard row, solved by existing off-the-shelf tech. Genuinely worth doing before or alongside any robot work, since it needs none of the navigation/LLM foundation above.

Open questions to settle together

  • How many zones does the real layout need — one per bed cluster, one per orchard row group, plus one for the compost strip's cover crop?
  • Tie into Home Assistant now, so it's already a callable function once the robot architecture exists?
Next step: worth speccing this one independently of the robot timeline — it pays off immediately either way.

Fixed Sensors + Dashboard

No robot needed — can start anytime

The plan's other easy win: soil moisture sensors and a static camera on one area, feeding a garden-monitoring dashboard to cut down on manual checking walks. This dashboard is also exactly what step 4+ of the robot build order needs anyway — worth building once and reusing.

Open questions to settle together

  • Which spots get a fixed sensor first — the annual beds (higher water need, more attention) or the orchard (lower frequency, but a bigger area to check)?
  • Same dashboard as the robot's status/API from the architecture above, or a separate simpler one to start?
Next step: good candidate to build in parallel with the Weeder — shares no hardware, so it doesn't block or get blocked by robot decisions.
